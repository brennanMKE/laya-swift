# Golden fixtures

Everything here is generated by [`tools/make_golden.py`](../../tools/make_golden.py) from the
Python reference and checked by Go tests. Don't edit these files by hand; regenerate them when
the Python reference or the checkpoint changes.

`meta.json` records what produced them:

| Field | Value |
|---|---|
| `versions` | laya 0.3.6, torch 2.14.0, transformers 5.17.0, tokenizers 0.23.2, numpy 2.5.3 |
| `revision` | checkpoint `convaiinnovations/laya@1c5edc17a7acd8701df6fc341c0d179f1c62c982` |
| `device`, `dtype` | `cpu`, `float32` (`laya.Agent(dir, device="cpu")`) |
| `max_len`, `head_max_len` | 512, 192 |
| `temperature`, `temperature_by_options` | the fitted values as shipped, before the [0.5, 5.0] clamp |

The fixtures were generated on macOS arm64. That matters only for calibration: numpy's float32
`exp` is the platform's `expf` (see [Tolerances](#tolerances)).

## Regenerating

```sh
PY=../System1Arcade/.venv/bin/python
$PY tools/make_golden.py capture      # plays the games, writes corpus/games.jsonl.gz (~1 min)
$PY tools/make_golden.py generate     # runs the reference, writes everything else (~30 min on CPU)
```

`capture` builds System 1 Arcade's `cmd/headless`, starts it on a free port, and plays Tetris,
Frogger and Space Invaders (seeds 1–6, up to 400 decisions each) in lockstep with the oracle's
answers (`GET /v1/laya`, `GET /v1/oracle`, `POST /v1/decide`). It keeps each distinct `/v1/laya`
body. `generate` picks the game requests to keep (every request that adds a new (state,
question) pair, then a random fill up to 150 per game), adds the hand-written edge cases, and
runs the reference. It reads the checkpoint from the local Hugging Face cache (`--model` to
override) and never downloads.

## Files

| File | Records | What it pins |
|---|---|---|
| `corpus/games.jsonl.gz` | 2,824 captured requests | input only: the raw game corpus `generate` samples from |
| `games.jsonl` | 343 requests (150 Tetris, 150 Frogger, 43 Invaders) | real game prompts end to end |
| `edge.jsonl` | 47 requests | hand-written edge cases (below) |
| `calibration.jsonl` | 264 questions | calibration and rounding alone, from synthetic logits |
| `tokenizer.jsonl` | 6,511 strings | tokenizer ids alone |
| `trace/*.safetensors` + `trace/index.json` | 5 sequences | every intermediate tensor, for bisecting the forward pass |

All JSONL files are one compact JSON object per line, UTF-8, non-ASCII unescaped, key order as
Python produced it.

### Float encoding

Every logit is a float32 written as the shortest decimal that round-trips it as a float32 (for
example `20.911156`). Parse with `strconv.ParseFloat(s, 32)` to get the exact float32 back. Don't
parse as float64 and compare; do convert to `float32`.

Answer numbers (`probabilities`, `confidence`, …) are Python floats after `round(x, 4)`, written
with Python's `repr`.

### `games.jsonl` and `edge.jsonl`

```jsonc
{
  "id": "tetris-0000",            // or "edge-012"
  "source": "tetris",             // "tetris" | "frogger" | "invaders" | "edge"
  "note": "seed 1 decision 0",    // what the case is
  "request": {…},                 // the /predict body, exactly as the game sent it:
                                  //   {"state", "questions"} or {"batch": {key: {"state", "questions"}}}
  "sequences": [                  // one per question, batch keys in order, then questions in order
    {
      "key": "p1s1",              // batch key; "" for a single-state request
      "question": "look",         // question name
      "qtype": 0,                 // 0 choice, 1 score, 2 noul (the type_emb row)
      "n_options": 2,             // len(render_options(q))
      "ids": [50281, …, 50282],   // build_sequence ids: [CLS] … [SEP], ≤ 512
      "markers": [15, 22],        // [MASK] positions, one per option that fit
      "logits": [5.51, -0.51],    // raw scorer logits from the batched pass (predict_many)
      "act_logits": [3620.3, …],  // raw act-head logits [act, escalate] from the batched pass
      "logits_single": […],       // the same from the per-state pass (Agent.predict)
      "act_logits_single": […]
    }
  ],
  "predict_many": {key: {question: answer}},   // laya_batch.predict_many(agent, batch)
  "predict": {key: {"model", "answers": {question: answer}, "usage": {"input_tokens", "output_tokens"}}},
                                               // agent.predict(state, questions) per key
  "error": "question o.q options exceed head_max_len=192"   // only when Python raises
}
```

- **The batched pass** runs every sequence of the request in one padded batch, the way
  `laya_server.py` answers `{"batch": …}`. **The per-state pass** runs one `Agent.predict` per
  key, the way it answers `{"state", "questions"}`. The two passes pad differently, so their
  logits differ by float noise (at most 3.7e-5 across these fixtures). Each answer set is
  paired with the logits of its own pass.
- When `error` is present, Python refused the request. `sequences` still holds what
  `build_sequence` returned: `markers` is then shorter than `n_options`. There are no logits or
  answers.
- `usage.input_tokens` is the sum of `len(ids)` over that state's sequences.
- **What the forward-pass port should compare:** `ids`, `markers` and `qtype` are the engine's
  input (the `engine.Batch`); `logits` / `act_logits` are its expected output. Run all sequences
  of a record as one batch and compare against `logits`, or each key alone and compare against
  `logits_single`. Both are fp32 CPU PyTorch.

Edge cases in `edge.jsonl` (see `edge_cases()` in the script): NFC and non-NFC text, CJK,
emoji with ZWJ, RTL and Indic scripts, Unicode spaces and digits, control characters,
contractions, runs of 2–60 spaces, tabs and newlines, `[SEP]`/`[CLS]`/`[MASK]`/`[unused0]`/
`|||EMAIL_ADDRESS|||`/`<|endoftext|>` inside states, `[MASK]` in instructions and options,
list-valued choice criteria, `None`/`""`/`0`/`false` descriptions, dict- and list-valued
criteria, a one-option choice, noul with custom and partial descriptions, 2-, 5- and 8-level
scores, mixed types in one request, non-string instructions, 4/6/10/11/15/30 options (every
temperature bucket, including the clamped `choice:11+`), options squeezed to the per-option
budget, an option cut at 48 tokens, instructions cut to the head budget, 140 options (the
`options exceed head_max_len` error), states of 40–1,200 words (sliding window and truncation
at 512), JSON states (key order, nesting, big ints, `-0.0`, `1e22`, `5e-324`, escapes, U+2028),
list states, a batch mixing all of these, and an empty state.

### `calibration.jsonl`

```jsonc
{"id": "cal-000", "type": "choice", "k": 1,
 "logits": [0.0], "act_logits": [-1.23, -0.66],
 "question": {"type": "choice", "instructions": "c", "criteria": {"o0": ""}},
 "predict_many": {answer}, "predict": {answer}}
```

The model is replaced by a stub that returns `logits` and `act_logits`, and the real
`predict_many` and `Agent.predict` produce the answers. Shapes: choice with 1–12, 15, 20 and 40
options, score with 2, 3, 5, 6, 8 and 11 levels, and noul; per shape, all-equal logits,
near-ties, a wide spread, one huge gap, and random logits.

### `tokenizer.jsonl`

`{"text": "…", "ids": [...]}`, from `agent.tok(text, add_special_tokens=False)`. The strings are
every game state and instruction, 3,000 seeded random strings over a mixed alphabet (scripts,
combining marks, Unicode spaces, contractions, special and added tokens), 3,000 seeded random
strings of code points from every plane mixed with ASCII, and the first 400 lines of
`make_golden.py` itself (code and English prose).

Strings where tokenizers' own NFC normalizer disagrees with `unicodedata.normalize("NFC")` are
left out and counted when generating (none in the current set). tokenizers normalizes with the
`unicode-normalization-alignments` crate, whose Unicode tables are older than Python's and
Go's `x/text` (Unicode 17): for example it leaves `U+030F U+07FD` unordered, which newer tables
reorder. A 20,000-string run over random code points found this as the only difference (1
string); it can only matter for combining marks added in recent Unicode versions.

### `trace/`

One safetensors file per sequence: tetris, frogger and invaders (the first game prompt of
each), `score` (a 5-level score question) and `long` (a 120-word state, 195 tokens, so the
sliding window is active). Each sequence was run alone (batch of one, no padding) and holds
float32 tensors:

| Tensor | Shape | Meaning |
|---|---|---|
| `emb` | [L, 1024] | embeddings output: `LayerNorm(tok_embeddings[ids])` |
| `layer.0`, `layer.1`, `layer.2`, `layer.3`, `layer.27` | [L, 1024] | output of that encoder layer (before the final norm) |
| `final_norm` | [L, 1024] | encoder `last_hidden_state` |
| `head_in` | [L, 1024] | `final_norm + type_emb[qtype]` (the head's input) |
| `head.0`, `head.1` | [L, 1024] | output of each head layer |
| `logits` | [k] | scorer logits at the markers |
| `act_logits` | [2] | raw act-head logits |

The header metadata has `ids`, `markers` (JSON arrays) and `qtype`. `index.json` lists each
file with its state, question, ids, markers and tensor shapes.

## Tolerances

What the Go tests require today:

| Check | Required | Result |
|---|---|---|
| Token ids, marker positions, option counts (`games`, `edge`) | identical | identical on all |
| Tokenizer ids (`tokenizer.jsonl`) | identical | identical on all (see the NFC note above) |
| Answers from Python's logits, both shapes, after 4-decimal rounding (`games`, `edge`, `calibration`) | identical JSON text | identical on all |
| `usage.input_tokens` | identical | identical on all |

Calibration follows numpy's float32 arithmetic step by step (float32 temperature division,
float32 `exp` and `log`, numpy's pairwise summation order). The one step Go can't copy
portably is `exp`: numpy calls the platform's `expf`, and macOS's differs from the correctly
rounded result by one ulp for about 0.6% of inputs. Measured over 200,000 random questions,
that changed a 4-decimal answer for 2 of them. None of the fixtures hit it.

For the forward pass, the design's tolerances apply: raw logits within 1e-3 of `logits`
(expect ~1e-5), calibrated probabilities within 5e-4, and 4-decimal answers equal in at least
99% of fields.
